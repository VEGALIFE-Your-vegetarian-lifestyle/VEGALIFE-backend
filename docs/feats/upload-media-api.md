# Feature Spec: Upload Media API (Presigned URL)

## Status

In progress

## Author / owner

Vegalife backend team

## Summary

Let an authenticated user obtain a short-lived, signed upload grant from the backend, push the file straight to the object store, and confirm the upload so the backend records the resulting media and returns its media ID.

## Problem / motivation

The `media` table (migration `V4__create_media_table.sql`) and `PostService.resolveMedia()` already exist, and `PostCreateRequest.mediaId` already accepts an uploaded video — but there is no endpoint that gets a file into the store in the first place. `media_url` is `NOT NULL` today, so the schema cannot even represent a row that is mid-upload. Video posts therefore cannot be created end to end.

## Goals

- Give a signed-in user a way to start an upload and, after the bytes land, obtain a `mediaId` that `POST /api/posts` accepts.
- Enforce an image/video type allowlist and a configurable per-type size ceiling, checked again authoritatively after the upload.
- Keep the backend off the file transfer path: it issues a grant and verifies afterwards, it never proxies bytes.

## Non-goals

- Direct upload through our own API (the grant is the only path).
- Image/video transformation, transcoding, or thumbnail generation.
- CDN configuration and cache invalidation.
- Deleting media, listing media, or a media picker endpoint.
- Ownership enforcement on media (see "Risks / open questions").
- Selecting or abstracting multiple storage providers in this PR — only Cloudinary is shipped; the seam exists so another provider can be added later.

## Requirements

### Functional Requirements

- [ ] FR-001: `POST /api/media/upload` requires a valid JWT and records the authenticated user as the media owner.
- [ ] FR-002: The request carries `contentType` (required), and optionally `fileName` and `sizeBytes`; `contentType` must be one of `image/jpeg`, `image/png`, `image/webp`, `video/mp4`, `video/webm`, otherwise the call returns `400`.
- [ ] FR-003: A request whose declared `sizeBytes` already exceeds the ceiling for its media class returns `400` without creating a row or contacting the provider.
- [ ] FR-004: The endpoint persists a `media` row in status `uploading` with `media_url` null, then returns `201 Created` with the media ID, the upload expiry, and a uniform upload instruction (`method`, `url`, `headers`, `fields`).
- [ ] FR-005: The `public_id` returned in `fields` is derived server-side from the media ID and the owner's user ID; the client cannot choose it.
- [ ] FR-006: `max_file_size` is present in `fields` as advisory metadata and `allowed_formats` is part of the signed parameters, so the provider rejects a non-conforming format at upload time. Cloudinary does not enforce `max_file_size`, so size enforcement rests on FR-003 and FR-010.
- [ ] FR-007: `POST /api/media/{mediaId}/confirm` takes no body; the server derives the `public_id` from the stored row, asks the provider whether that object exists, and reads back its real size, format, dimensions and delivery URL.
- [ ] FR-008: On a successful confirmation the row moves from `uploading` to `succeed` and stores `media_url`, `file_size_bytes`, `mime_type`, `width`, `height`, and `external_id`; the endpoint returns `200` with the media DTO.
- [ ] FR-009: If the provider reports no such object, confirmation returns `400 Upload verification failed` and the row stays `uploading`.
- [ ] FR-010: If the provider reports a real size above the ceiling for the row's media class, confirmation returns `400` with the limit message, records `status = failed`, and the row can never be attached to a post.
- [ ] FR-011: Confirming a row that is already `succeed` returns `409 Media upload has already been confirmed`.
- [ ] FR-012: A confirmation attempted after the grant TTL has elapsed returns `400 Upload grant has expired`.
- [ ] FR-013: `GET /api/media/{mediaId}` returns `200` with the media DTO for an existing row and `404 Media not found` otherwise.
- [ ] FR-014: All limits and the provider credentials are configuration under `app.media.*`; no type list or byte count is a code constant.

### Non-Functional Requirements

- [ ] NFR-SEC-001: The signed `fields` are generated by the provider SDK from the server-held secret; the API secret is never returned to the client or logged.
- [ ] NFR-SEC-002: Confirmation does not trust any client-supplied URL, size, format or provider identifier — every value is read back from the provider.
- [ ] NFR-SEC-003: Ownership of a media row is derived from the authenticated JWT, not from a request field.
- [ ] NFR-MAINT-001: Provider-specific code is confined to a single `PresignedUploadProvider` implementation; controller, service, DTOs and repository are provider-agnostic.
- [ ] NFR-MAINT-002: Integration tests run against an in-process fake provider bean, requiring no network access and no provider credentials.

## Design overview

One shared orchestration path plus one provider seam:

- `MediaController` — `POST /api/media/upload`, `POST /api/media/{mediaId}/confirm`, `GET /api/media/{mediaId}`; extracts the JWT principal, validates the DTO, returns `ApiResponse`.
- `MediaService` — owns the `Media` lifecycle (`uploading` → `succeed` / `failed`), size and type enforcement, grant expiry, and mapping to `MediaResponse`.
- `MediaProperties` (`app.media.*`) — Cloudinary credentials plus upload limits; bound with `@ConfigurationProperties`.
- `PresignedUploadProvider` — interface with `prepare(...)` (produce the upload instruction) and `verify(...)` (report whether the object exists and what it is).
- `CloudinaryUploadProvider` — the only class that touches the Cloudinary SDK. `prepare` builds the signed params; `verify` calls the Admin API for the stored `public_id`.

Migration `V20__add_media_upload_lifecycle.sql` makes `media_url` nullable (an `uploading` row has no URL yet), adds `media.uploaded_by` (AC: media is linked to a user) and `media.external_id` (the provider object key, so confirmation does not depend on a naming convention).

The client-facing upload instruction has a fixed shape regardless of provider, so the frontend has a single code path.

## Success metrics

Before merge: the build, unit tests, Checkstyle and Spotless gates all pass, and integration tests cover grant creation, successful confirmation, provider-not-found, over-size rejection, repeat confirmation, and unauthenticated access. Production usage metrics are not available yet.

## Acceptance criteria

**As an** authenticated user, **I want to** upload an image or video through a signed URL, **so that** I get a media ID I can attach to my post without the file passing through the backend.

- [ ] Given a valid JWT and an allowed `contentType`, when the user requests an upload, then the API returns `201` with a media ID, an expiry, and upload fields that the provider will accept.
- [ ] Given a `contentType` outside the allowlist (for example `application/pdf`), when the user requests an upload, then the API returns `400` and no media row is created.
- [ ] Given a declared `sizeBytes` above the class ceiling, when the user requests an upload, then the API returns `400` and the provider is not contacted.
- [ ] Given a granted upload, when the user posts the file to the provider and then calls confirm, then the API returns `200` with `status: succeed` and a delivery URL, and `POST /api/posts` accepts that `mediaId`.
- [ ] Given no file was ever uploaded, when confirm is called, then the API returns `400 Upload verification failed` and the row stays `uploading`.
- [ ] Given an uploaded object larger than the ceiling, when confirm is called, then the API returns `400` with the limit message and the row is `failed`.
- [ ] Given an already-confirmed row, when confirm is called again, then the API returns `409`.
- [ ] Given no JWT, when any of the three endpoints is called, then the API returns `401`.

## Risks / open questions

- **Media ownership is not enforced on attachment.** Per the product decision for this issue, attaching another user's media to one's own post is considered acceptable, so `PostService.resolveMedia()` still checks only `status == succeed`. The new `uploaded_by` column makes an ownership check a one-line addition if that stance changes.
- **Orphan rows.** A client that requests a grant and never uploads leaves a permanent `uploading` row with a null URL. Harmless because nothing can reference it, but a sweeper is a candidate follow-up.
- **`max_file_size` provider-side behaviour is verified as unenforced.** Live probes on 2026-10-02 confirmed Cloudinary does not enforce it (a `max_file_size=1` grant accepted a 70-byte file) and excludes it from its signature verification string — signing it caused the 401s of issue #38. The field is still returned for client visibility; confirmation re-checks the reported `bytes` (FR-010), so enforcement never depended on the provider honouring it.
- **Flyway `out-of-order` is enabled for this branch.** `spring.flyway.out-of-order` is turned on so that `V19__add_post_filtering.sql` (open PR) can land after `V20`. V19 and V20 touch disjoint tables (`post` vs `media`), so the late application is safe here. This weakens Flyway's "next number wins" guard for future parallel branches and is recorded in `docs/brs/media.md` (BR-MEDIA-006).
